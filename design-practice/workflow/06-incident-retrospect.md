# Incident Retrospect — 设计复盘工作流（事故→规则）

> 出处:原文行 2307-2323。原文金句:**"如果上线后出了问题,不要只怪某个人粗心。要问系统哪里漏了。"**
>
> 原文金句:**"真正成熟的团队,不是永远不犯错,而是每犯一次错,都把错误沉淀成规则。"**

## 为什么需要这个工作流

skill 当前所有工作流（10 步 / 8 步 / Stage 0/1/2 / 改造四步）的闭环都在"上线"或"ship"就断了。`workflow/01-ten-step-flow.md` 的 Step 10 只说"把发现的新模式/新反例/新状态/新文案沉淀回设计系统"——这是口号,不是 SOP。

**缺的是回路**:上线后出事故 → 怎么从一次事故走到一条新规则?触发器是什么?沉淀到哪个文件?谁负责?截止什么时候?

这个工作流填这个洞。

## 触发条件（什么时候跑这个流程）

| 触发场景 | 怎么识别 |
|---|---|
| P0 上线后翻车 | 用户报告"创建任务失败"、"提交丢内容"、"权限错了" |
| 用户反馈"这里不好用" | 不是 bug 但体验差,用户重复抱怨 |
| 同一个问题修了 3 次还没修干净 | 说明根因没找到,只修了症状 |
| QA 漏检了一个状态 | 上线后才发现某个状态/边界没覆盖 |
| 设计评审反复出同样的问题 | 多次评审都发现"主按钮超过 1 个"、"状态漏 loading"——说明系统没规则 |

**触发纪律**:任何一次 P0 / 用户抱怨 / 同样问题第 3 次出现,**必须**跑这个流程。否则经验只在个人脑子里,下次还会犯。

## 复盘六问（原文行 2307-2323 verbatim）

> 原文:**"不要只怪某个人粗心。要问系统哪里漏了。"**

```text
复盘六问（事故定位,逐条答):

1. 提示词没写状态?
   （是不是因为我生成时没在 prompt 里列 8 态/5 态要求?）

2. 组件库没有这个状态?
   （是不是因为 components/button.md 没写"长时间 loading + 取消"这个状态?）

3. 验收清单没覆盖?
   （是不是因为 qa-state-acceptance.md 没列"网络抖动重连"这个边界?）

4. 设计评审没问到?
   （是不是因为评审 SOP 没问"网络抖动怎么办"?）

5. 代码评审只看能跑?
   （是不是因为代码评审只看了功能跑通,没看异常分支?）

6. 需求一开始没讲清用户?
   （是不是因为需求阶段没明确"用户在地铁里用,网络会抖动"?）
```

**纪律**:六问必须**逐条答**,不能合并成"系统有问题"。合并=走过场。每条要么"是"（说明根因）,要么"否"（说明为什么不是这一层）。

## 事故→规则沉淀表（模板）

```text
事故 → 规则沉淀表

事故描述:
- 时间:
- 现象（用户看到什么）:
- 影响（多少用户、多严重）:
- 触发条件（什么情况下复现）:

根因层（六问答案）:
- 1 提示词:是/否,说明
- 2 组件库:是/否,说明
- 3 验收清单:是/否,说明
- 4 设计评审:是/否,说明
- 5 代码评审:是/否,说明
- 6 需求:是/否,说明

沉淀动作（每条根因层对应一条规则更新）:
| 根因层 | 沉淀到哪个文件 | 具体规则 | Owner | 截止 |
|---|---|---|---|---|
| 2 组件库 | components/button.md | 新增"长时间 loading + 取消按钮"状态 | @xxx | 2026-07-05 |
| 3 验收清单 | references/qa-state-acceptance.md | 新增"网络抖动重连"边界检查 | @xxx | 2026-07-05 |

后续验证:
- 规则更新后,跑一遍 qa-p0p1p2 看新规则生效
- 下一次类似场景,确认不再翻车
```

## 沉淀规则（原文行 2321-2323 verbatim）

> 原文金句:**"今天漏了空状态,明天清单里就加空状态;今天重复提交出事故,明天按钮规范里就加 loading 锁定;今天抽屉移动端不好用,明天响应式规则里就加抽屉移动端策略。"**

**沉淀原则**:

1. **每次事故必须沉淀到一条具体规则**——不能只修代码,不更新规则。只修代码=同一问题下次还会犯。
2. **规则沉淀到现有文件**——不要建新文件。`components/button.md` 缺状态就加到那里,`qa-state-acceptance.md` 漏检查就加到那里。新建文件会让 skill 越来越碎。
3. **规则要具体可执行**——不是"注意网络抖动",而是"网络抖动时,提交按钮进入 loading 但不 disable,旁边出现'网络不稳,重试'文字按钮"。规则要让 Agent 能照着做。
4. **沉淀有 Owner 和截止**——没有 owner 和截止的沉淀等于没沉淀。复盘会议必须当场指派。

## 和 patterns/05-design-system-governance.md 的边界

| 文件 | 范围 | 何时跑 |
|---|---|---|
| `patterns/05-design-system-governance.md` | **系统级 review**——定期（每月/每季度）检查 token / 组件 / 模式的健康度,看有没有冗余、缺失、腐化 | 主动周期性 |
| `workflow/06-incident-retrospect.md`（本文） | **事故级复盘**——出事后立刻跑,从一次事故走到一条新规则 | 被动触发 |

两者正交,不能互替。系统级 review 不能替代事故复盘,事故复盘也不能等到下次系统 review 才做。

## 在 skill pipeline 里的位置

```
workflow/01 10 步流程 / workflow/05 8 步项目 / workflow/07 改造四步
   ↓
qa-p0p1p2 验收 → qa-polish 打磨
   ↓

   ↓

   ↓

```

这是 skill 从"生成器"升级为"能自我进化的系统"的关键一环。**没有这条回路,设计能力只能留在个人脑子里,无法沉淀进系统。**

## 反模式

| 反模式 | 为什么坏 | 修正 |
|---|---|---|
| 上线后翻车只修代码,不更新规则 | 同一问题下次还会犯 | 强制跑复盘六问,沉淀到具体文件 |
| 复盘只怪某个人粗心 | 个人问题没法复用,系统漏洞没堵 | 问"系统哪里漏了",不问"谁粗心" |
| 六问合并答"系统有问题" | 走过场 | 逐条答,每条要么是（说明根因）要么否 |
| 沉淀建新文件 | skill 越来越碎 | 沉淀到现有 components/qa-*/patterns/ 文件 |
| 沉淀没有 owner 和截止 | 等于没沉淀 | 复盘会议当场指派 |
| 等下次系统 review 才做事故复盘 | 等到那时已经忘细节 | 出事后 24-48 小时内跑 |
