## 盲点 1【P0】设计复盘 / 事故沉淀为规则——skill 完全缺失"复盘"环节

**原文行号**:行 2307-2323(第十编 五"复盘:每次事故都要回到系统")+ 行 2325-2327 小结 + 行 2786"用验收清单结束每一次工作"

**原文核心**:
> "如果上线后出了问题,不要只怪某个人粗心。要问系统哪里漏了:是提示词没写状态?是组件库没有这个状态?是验收清单没覆盖?是设计评审没有问到?是代码评审只看能跑?是需求一开始就没讲清用户?**真正成熟的团队,不是永远不犯错,而是每犯一次错,都把错误沉淀成规则**。"

原文给了**复盘六问**(漏点定位):
1. 提示词没写状态?
2. 组件库没有这个状态?
3. 验收清单没覆盖?
4. 设计评审没问到?
5. 代码评审只看能跑?
6. 需求一开始没讲清用户?

并给了沉淀规则:**"今天漏了空状态,明天清单里就加空状态;今天重复提交出事故,明天按钮规范里就加 loading 锁定;今天抽屉移动端不好用,明天响应式规则里就加抽屉移动端策略。"**

**skill 现状**:
- `grep 复盘` 全 skill 只命中 `source-full.md` 一处(原文本身),**没有任何复盘工作流文件**。
- `patterns/05-design-system-governance.md` 只讲"谁定期 review 系统健康度"(系统级 review),**不是事故级复盘**,且没给复盘模板、没给"事故→规则"沉淀 SOP。
- `workflow/01-ten-step-flow.md` 的 Step 10"沉淀"只说"把发现的新模式/新反例/新状态/新文案沉淀回设计系统",**没说怎么从一次事故/一次 P0 漏掉走到一条新规则**,缺触发器与模板。

**为什么 P0**:这是原文明确点名的"成熟团队 vs 不成熟团队"的分水岭,且 skill 当前的工作流闭环在"上线"就断了——`Step 9 验收` 之后只有一句口号式 `Step 10 沉淀`,**没有"上线后出事故→回到六问→落到具体规则文件"这条回路**。设计能力如果不闭环回系统,经验就会流失,正是原文反复警告的"让下一次不要靠记忆解决,让系统替团队记住"。

**建议补**:新建 `workflow/06-incident-retrospect.md`,内容 = 复盘六问模板 + "事故→规则"沉淀表(事故描述 / 根因层 / 沉淀到哪个文件 / owner / 截止)+ 与 `patterns/05-design-system-governance.md` 的挂载点(谁负责把规则写进组件状态/验收清单/P0 判定标准)。

## 盲点 2【P0】五层刀法的"非 token 层完整拆解"——armory 只有 ④System 层,①②③⑤ 层缺失

**原文行号**:行 2339-2351(五层刀法定义)+ 2353-2383(Linear)+ 2385-2411(Stripe)+ 2412-2442(Apple)+ 2444-2460(Notion)

**原文核心**(行 2343-2350 五层定义 verbatim):

| 层级 | 要拆什么 | 核心问题 |
|---|---|---|
| 第一层:**任务** | 用户来办哪件事 | 它把哪条主流程做顺了? |
| 第二层:**结构** | 页面、导航、容器、分组 | 信息为什么这样安排? |
| 第三层:**状态** | 加载、空、错、权限、离线 | 出事时它怎么稳住用户? |
| 第四层:**系统** | 令牌、组件、模式、一致性 | 它如何让多页面不走样? |
| 第五层:**气质** | 文案、动效、节奏、品牌 | 它为什么让人觉得可靠或高级? |

并且原文每个案例都拆到了具体细节,例如:
- **Linear**(行 2373-2379):① 减少视觉噪音(边框只在需要区分时出现)② 照顾高频用户(快捷键、命令菜单、快速创建、快速跳转)③ 状态安静但明确(任务状态/优先级/负责人/项目归属都能扫读)
- **Stripe**(行 2393-2403):标题先讲结论 / 代码说明互相对照 / 状态写得很具体 / 视觉层级稳定 / 品牌色小面积
- **Apple**(行 2416-2426):从人体出发 / 从平台习惯出发 / 从情境出发 / 从一致性出发
- **Notion**(行 2450-2456):底层自由(块/数据库/页面/关系/模板)+ 上手扶梯(模板/空状态/命令菜单/示例内容)

**skill 现状**:
- `references/case-studies.md`:**五层全拆了**(Linear/Stripe/Apple/Notion 各一张 ①-⑤ 表),但每层只有一句话,深度浅。
- `patterns/07-case-dissection-dictionary.md`:把五层刀法和四大样板判断都搬过来了,**比 case-studies.md 更完整**,但仍然是"判断层"的总结,**不是"可还原的拆解"**。
- `references/armory/01-tokens-linear.md`、`02-tokens-stripe.md`、`03-tokens-notion.md`:**只拆 ④System 层**(color/space/radius/font/component token),①Task ②Structure ③State ⑤Tradeoff 完全不在 armory 里。
- `references/stage1-five-layer.md`:**讲的是"反向使用五层刀法"——把刀法用来生成**(从任务层往外长),**不是"正向拆解已存在产品"**。这两件事用的是同一个框架,但用途相反。
- **Apple 完全没有 armory 文件**(`00-index.md` 写"Apple HIG → 04-tokens-material3.md(下册)"但 04 文件实际不存在,Glob 只返回 01/02/03)。

1. 用户说"我要 Linear 风" → armory/01 给的是 tokens,即 ④System 层。
2. 用户说"拆 Linear 给我看" → case-studies.md / patterns/07 给的是五层一句话总结。
3. **没有任何文件能回答"Linear 在 ②Structure 层具体怎么排?③State 层具体怎么写?⑤Tradeoff 层砍了什么?"**——这些恰恰是原文反复强调的"好产品真正厉害的地方,藏在你第一眼看不到的地方:默认值、空状态、边界、键盘路径、错误恢复、权限说明、数据密度、信息取舍"(行 2335)。

## 盲点 4【P1】"每天看一个页面练眼睛"方法论——skill 缺"读图 checklist"

**原文行号**:行 2003-2033(第十编 一"每天看一个页面:先练眼睛")

**原文核心**:每天 20 分钟,按 5 层顺序拆:
1. **先看任务**(用户办什么事)
2. **再看主次**(主/辅/隐藏)
3. **再看路径**(下一步点哪、有没有分叉太多)
4. **再看状态**(加载/空/错/权限/离线在哪)
5. **再看细节**(文字/间距/对齐/颜色/动效有没有服务任务)

并给了**读图表格**(行 2023-2029):

| 每日拆解层级 | 要问的问题 | 容易看错的地方 | 真正该记下的经验 |
|---|---|---|---|
| 任务 | 用户来办哪件事? | 被视觉风格吸引 | 页面必须先有主任务 |
| 结构 | 信息怎么分组? | 只看单个组件 | 好页面先靠安排,不先靠装饰 |
| 状态 | 出事时怎么办? | 只看默认态截图 | 状态决定产品可靠感 |
| 边界 | 长文本、空数据、弱网会怎样? | 相信样例数据 | 坏数据最能验水平 |
| 细节 | 间距、对齐、动效是否稳? | 把细节当化妆 | 细节是秩序的外观 |

并给了**两个读图范例**(行 2019-2021):支付页 7 问、任务列表 6 问。

**skill 现状**:
- `references/qa-page-five-questions.md` 是"页面好坏五问",**用来评自己生成的页面**,不是用来读别人的页面练眼。
- `patterns/07-case-dissection-dictionary.md` 的五层刀法**理论上可以用来读图**,但定位是"拆案例建字典",**没明确说"这也是每天练眼睛的方法"**。
- **缺一个面向"用户丢一张截图过来,Agent 帮我按 5 层读"的提示词**。

**为什么 P1**:这是原文第十编第一节,排在工作法最前面,是"练眼睛"的入口。skill 如果能让 Agent 既"拆案例建字典"又"读截图练用户眼睛",就把第十编一、第十一编七两个案例提示词打通了。当前缺一个"读图 checklist 提示词"。

**建议补**:在 `patterns/07-case-dissection-dictionary.md` 末尾或新建 `patterns/08-daily-page-reading.md`,内容 = 5 层读图顺序 + 支付页/任务列表两个范例 + 读图提示词(用户贴截图,Agent 按 5 层 + 4 列"问什么/容易看错什么/该记什么"输出)。
