# patterns/07 — 案例拆解 + 案例库变设计字典

> 出处:《设计的实践》第 11 编(行 2302-2465)
> 定位:**学习世界级产品的方法论 + 把案例沉淀成可检索的设计字典**
>
> **作者原话**:「学世界级产品,不要学皮肤,要学判断。拆任务、拆结构、拆状态、拆系统、拆取舍,再把案例沉淀成自己的设计字典。**会拆案例的人,才会真正进步;只收藏截图的人,永远停在表面。**」

## 一、拆案例的五层刀法(原文核心)

> **作者金句(行 2305)**:「你看到的是皮肤,不是骨架。学产品,不能只学'长相',要学'做判断的方式'。好产品真正厉害的地方,往往藏在你第一眼看不到的地方:**默认值、空状态、边界、键盘路径、错误恢复、权限说明、数据密度、信息取舍**。」

### 拆解顺序(不能反)

| 层级 | 要拆什么 | 核心问题 | 看错时会怎样 |
|---|---|---|---|
| **第一层:任务** | 用户来办哪件事 | 它把哪条主流程做顺了? | 只看到漂亮截图,看不到业务价值 |
| **第二层:结构** | 页面、导航、容器、分组 | 信息为什么这样安排? | 照搬布局,却不适合自己的产品 |
| **第三层:状态** | 加载、空、错、权限、离线 | 出事时它怎么稳住用户? | 只抄默认态,一上线就崩 |
| **第四层:系统** | 令牌、组件、模式、一致性 | 它如何让多页面不走样? | 抄一个页面,做不成产品 |
| **第五层:气质** | 文案、动效、节奏、品牌 | 它为什么让人觉得可靠或高级? | 把气质误认为装饰 |

**关键纪律**:**你先看任务,就会问'它帮谁办什么事';你先看结构,就会问'为什么这样排';你先看颜色,就会忍不住问'这个蓝色是什么色值'。色值当然重要,但它排在后面。一个产品如果任务错了,颜色再准也没救。**

## 二、四大样板的核心判断(原文精华)

### Linear:克制不是少做,而是只让重要的东西出声

**核心用户**:每天处理 issue、项目、冲刺、优先级的软件团队。

**Linear 的克制不是审美洁癖,而是任务策略**:
- 常用操作足够近,低频操作足够安静
- 列表密度高,但层级不乱
- 快捷键强,因为老用户要速度
- 动效短,因为生产力工具不能拖泥带水
- 分割线弱,因为任务内容才是主角

**拆 Linear 要看三件事**:
1. 它怎样**减少视觉噪音**(边框只在需要区分时出现)
2. 它怎样**照顾高频用户**(快捷键、命令菜单、快速创建、快速跳转)
3. 它怎样让**状态安静但明确**(任务状态/优先级/负责人/项目归属都能扫读)

> **启发**:生产力工具的高级感,首先来自**不打扰**。用户每天用八小时的产品,不需要天天给他放烟花;它要像一把好刀,锋利、顺手、可靠。

### Stripe:可信感不是说出来的,是一层层铺出来的

**核心用户**:开发者(支付、账单、金融数据)。

**Stripe 没有把复杂藏没,而是把复杂排清楚**。它常用的手法:
- 标题先讲结论(文档页不是堆功能,而是先告诉开发者这一节解决什么问题)
- 代码和说明相互对照(文字解释、代码示例、参数说明、错误提示互相支撑)
- 状态写得很具体(支付失败、验证失败、权限问题,不会只说"错误",而是给开发者可行动的信息)
- 视觉层级稳定(大标题、说明、代码块、提示、链接各有声音,不抢话)
- 品牌色小面积使用(渐变是气质,不是到处乱撒)

**Stripe 给设计师最大的启发**:**复杂产品也可以清楚**。清楚不是少,而是把复杂分层。
- 开发者不是怕复杂,怕的是复杂没有结构
- 财务人员不是怕数字,怕的是数字没有解释
- 用户不是怕错误,怕的是错误不知道怎么修

### Apple:规矩不是限制创造,而是保护体验

**Apple HIG 最值得学的不是某个具体数值,而是它的思路:把大量经验写成可执行的规矩。**

**Apple 的规矩有几个特点**:
1. **从人体出发**:手指有大小、眼睛有极限、注意力会疲劳,所以点击区、字号、对比度都不能随便
2. **从平台习惯出发**:用户在一个系统里养成的预期,产品不该无故打破
3. **从情境出发**:手机、手表、平板、桌面、空间计算,设备不同,交互重心就不同
4. **从一致性出发**:同一种动作、同一种状态、同一种反馈,要让用户学一次,到处能用

**Apple HIG 的硬规矩(原文行 700-703)**:
- 点击区最小 44×44 点(Vision Pro 60×60)
- 安卓 Material Design 是 48×48 dp(约 9 毫米)
- 正文字号最小 11 点
- 正文对比度至少 4.5:1,大字至少 3:1
- 自定义按钮必须有"按下"状态

> **启发**:学 Apple,不是把你的产品做成 Apple 的样子,而是学它的态度:**把用户身体、设备环境、平台习惯和无障碍底线,当成设计的硬条件**。这些条件不是建议,是地板。

### Notion:自由产品最需要"扶上马"

**Notion 的设计难点**:自由和上手之间的矛盾。

**Notion 的块系统给了长期自由,但新人上手需要模板、示例、引导和默认路径。**

**拆 Notion 要看两面**:
1. **底层自由**:块、数据库、页面、关系、模板,让用户能拼出自己的系统
2. **上手扶梯**:模板、空状态、命令菜单、示例内容,让用户第一步不慌

> **启发**:**自由不是把用户扔进空地,而是给他积木、图纸和第一块砖**。任何自由度高的产品(低代码、AI Agent、知识库、数据分析、自动化平台),只要用户能组合很多东西,就必须给新手扶梯。**不要把"自由"当作不设计的借口。自由越大,引导越要清楚;能力越强,第一步越要简单。**

## 三、坏案例也要拆(失败比成功更诚实)

**只拆好产品还不够**。好产品容易让人崇拜,坏产品更能让人清醒。失败案例往往更诚实,因为问题暴露在表面:按钮太多、路径太乱、错误太含糊、状态缺失、权限不清、移动端崩坏。

**拆坏案例时,不要只骂"丑"**。丑只是结果,不是原因。要问:
- 它的主任务是什么?是不是根本没定清楚?
- 哪些功能在抢同一个位置?
- 哪些低频动作被放得太高?
- 哪些危险动作缺少确认?
- 哪些错误文案像系统日志?
- 哪些状态完全没设计?
- 哪些信息应该进抽屉或更多菜单,却被摊在主页面?

**坏案例改造三步**:
1. **标红问题**(不要急着重画,先把问题写出来)
2. **重排结构**(先解决主次、分组、路径)
3. **补齐状态**(最后补空、错、慢、权限、移动端)

> **启发**:**如果你能把十个坏页面改顺,比你收藏一千个好截图有用**。因为真实工作里,你要面对的多数不是完美新项目,而是已经长歪的旧页面。

## 四、案例拆解提示词(原文 verbatim,行 2419-2436)

```text
你是一位严厉的产品设计案例分析老师。
请不要写泛泛的"界面简洁、体验流畅",
而是按下面结构拆解这个产品/页面。

产品或页面:【填写名称或截图描述】

请输出:
1. 用户任务:这个页面主要帮谁完成什么事?
2. 信息结构:页面分为哪些区域?每个区域负责什么?
3. 主行动:一屏中最重要的行动是什么?是否唯一?
4. 状态设计:它如何处理 loading / empty / error / permission denied / offline?
5. 组件系统:按钮、表单、卡片、导航是否一致?
6. 视觉纪律:颜色、文字、间距、动效如何服务任务?
7. 取舍:它隐藏了什么?弱化了什么?为什么?
8. 可学习之处:我们的产品能学哪三点?
9. 不能照搬之处:由于用户、业务、平台不同,哪些不能抄?
10. 如果让我改进:给出 P0 / P1 / P2 建议。

要求:
- 每一条都要具体;
- 必须包含坏例风险;
- 不要用"高级感"这种空词,除非说明它由哪些具体设计造成。
```

## 五、把案例库变成设计字典(原文核心)

**长期成长,靠的不是临时灵感,而是自己的案例库**。

**案例库不要只是截图文件夹,而应该是一套可检索的设计字典**:

| 案例库字段 | 记录什么 | 为什么有用 |
|---|---|---|
| **产品名称** | Linear / Stripe / Notion / Apple / 其他 | 方便回查来源 |
| **场景** | 登录、支付、筛选、创建、删除、空状态 | **按问题查,而不是按产品查** |
| **用户任务** | 用户在这里要办什么事 | 防止只看风格 |
| **好设计做法** | 具体结构、文案、状态、动效 | 沉淀可复用方法 |
| **反面风险** | 如果做坏会怎样 | 形成设计警觉 |
| **可借鉴程度** | 可直接学 / 需调整 / 不适合 | 避免盲目照搬 |
| **提示词** | 如何让 AI 生成类似结构 | 把案例转成生产力 |

> **作者金句(行 2463)**:「当你的案例库积累到一百个,你会发现自己判断速度明显变快。遇到支付页,你脑子里会自动浮现 Stripe 的透明费用、错误处理和信任层级;遇到任务列表,你会想到 Linear 的密度和快捷路径;遇到自由编辑器,你会想到 Notion 的块、模板和新手扶梯。**设计经验就是这样长出来的:不是背概念,而是把一个个具体案例变成脑子里的参照物**。」

## 六、案例字典提示词(让 AI 帮你建字典)

```text
你是设计字典管理员。请基于下面案例,帮我建一条字典记录。

案例产品:{Linear / Stripe / Notion / 其他}
案例场景:{登录 / 支付 / 列表 / 详情 / 创建 / 删除 / 空状态 / 错误 / 权限 / 其他}
截图描述:{...}

请按以下字段填:

【产品名称】
【场景】
【用户任务】(具体,谁在办什么事)
【好设计做法】(列 3-5 条具体方法,不写空话)
【反面风险】(如果做坏会怎样,列 2-3 条)
【可借鉴程度】(可直接学 / 需调整 / 不适合 + 原因)
【提示词】(如何让 AI 生成类似结构,30-50 字)

纪律:
- 不写"高级感""现代感"空词
- 每条具体到结构/文案/状态/动效
- 提示词要可直接复用
```
