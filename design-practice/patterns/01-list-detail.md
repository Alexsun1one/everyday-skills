# patterns/01 — 列表-详情模式(复杂 App 的主干道)

> 出处:《设计的实践》第 16 章(行 6496–6663,原文 **61 次提及**,全书最高频)
> 严重度:★★★ — 这是 B 端产品最常见、最稳定、最耐用的主干道模式
>
> **适用**:CRM、订单系统、任务工具、邮件、issue 跟踪、工单、审批、内容管理、库存、人事、财务……几乎所有"先从一堆对象里找一个,再处理"的产品。

## 一句话

> **如果说页面是房间,导航是走廊,那么列表-详情模式就是复杂 App 里最常见、最稳定、最耐用的一条主干道。它解决的是"从一堆对象里连续处理多个对象"的工作流。**

## 认知路径(这是模式,不是版式)

这不是"左边列表右边详情"的版式,而是一条**认知路径**:

```
用户先扫一批对象
   ↓
用户找到值得处理的对象
   ↓
用户进入对象详情
   ↓
用户查看状态、历史、关系和可操作项
   ↓
用户处理完,再回到列表继续下一个
```

差设计会把这条路做断:
- 列表信息不够 → 用户不知道点哪个
- 详情没上下文 → 用户忘了从哪来
- 返回后列表位置丢了 → 用户又要从头找

好设计会让这条路像顺滑的传送带:**扫、点、看、改、回**,动作自然连续。

## 列表不是数据仓库,是决策前台

**最大的新手病**:把数据库字段直接投影到列表。

正确的问法不是"字段有哪些",而是:**用户扫这一页时,靠哪些信号做决定?**

### 列表必答三问

| 问题 | 列表要给什么 |
|---|---|
| **这是什么?** | 身份信息(任务标题、客户名、订单号) |
| **现在处于什么状态?** | 状态信息(进行中、逾期、已付款) |
| **我为什么要点它?** | 优先级 / 风险 / 行动提示 |

### 列表的 5 类信息

| 信息类型 | 作用 | 例子 | 常见错误 |
|---|---|---|---|
| 身份信息 | 让用户知道这是谁/是什么 | 任务标题、客户名、订单号 | 只显示 ID,不显示人能读懂的名称 |
| 状态信息 | 让用户知道现在怎么样 | 进行中、逾期、已付款、待审核 | 状态藏太深,必须点详情才知道 |
| 优先级信息 | 帮用户决定先处理谁 | 高优、阻塞、即将到期、金额大 | 所有行长得一样,没轻重 |
| 归属信息 | 告诉用户责任和关系 | 负责人、所属项目、客户公司 | 出了问题不知道找谁 |
| 行动提示 | 暗示下一步 | 需要审批、可退款、可重新发送 | 列表只能看,不能快速处理 |

## 列表密度:信息多 ≠ 拥挤

列表的永恒矛盾:信息少 → 用户判断不了;信息多 → 界面容易乱。高手不是"多放"或"少放",而是**分层放**。

### 列表三眼信息分层

```
列表行信息
   ├── 第一眼:身份 + 状态 + 关键风险(必须一眼可见)
   ├── 第二眼:负责人 + 时间 + 标签(扫视时看见,不抢主视觉)
   └── 第三层:历史 + 备注 + 低频操作(默认隐藏,进详情/hover/更多菜单)
```

**AI 产物最大问题 = 平均主义**:所有文字差不多大,所有标签差不多亮,所有按钮都摆出来。结果用户看见一堆东西,却抓不住重点。

> **列表页要像一张战情表:红灯在哪里、谁负责、下一步是什么,必须醒目。**

## 详情页不是字段堆叠,是对象的现场

详情页的任务,是让用户理解一个对象的**完整现场**:它是什么、现在怎样、和谁有关、发生过什么、我能做什么。

### 详情五区(必填)

| 区域 | 作用 | 例子 |
|---|---|---|
| **标题区** | 确认对象身份和关键状态 | 任务名、订单号、客户名、状态标签 |
| **主信息区** | 展示用户判断所需的核心内容 | 描述、金额、需求、地址、当前进度 |
| **属性区** | 展示可编辑的结构化字段 | 负责人、截止日期、优先级、阶段 |
| **关系区** | 展示对象和其他对象的连接 | 关联项目、关联客户、子任务、文件 |
| **历史区** | 解释对象如何变成现在这样 | 评论、活动日志、审批记录、版本历史 |

**详情最忌讳"把所有字段从上到下排一遍"。字段不是信息架构,字段只是原料,详情页要把原料组织成现场。**

## 三种打开方式决策树

```
点击列表项
   │
   ▼
详情复杂度如何?
   │
   ├── 轻量查看 / 快速编辑 ───────────────> 右侧抽屉
   │                                       (保留列表上下文)
   │
   ├── 需要连续处理多个对象(桌面大屏)──> 左右分栏
   │                                       (列表+详情同时常驻)
   │
   └── 信息量大 / 流程长 / 可分享 URL ──> 整页详情
                                           (空间大,可深读)
```

| 形态 | 适合 | 优点 | 风险 |
|---|---|---|---|
| 整页详情 | 对象复杂、需深度处理、需分享 URL | 空间大、结构完整 | 上下文切换较重 |
| 右侧抽屉 | 快速查看、轻量编辑 | 保留列表上下文 | 空间有限 |
| 左右分栏 | 桌面高频处理多对象 | 列表+详情常驻,效率高 | 移动端难适配 |

**成熟产品常常三者都有**:默认抽屉快速看 → 点"打开完整页面"进整页 → 桌面大屏支持分栏 → 移动端改路由跳转。这不是重复,是给不同场景不同速度。

## 列表-详情的状态矩阵(必须全覆盖)

| 状态 | 列表侧 | 详情侧 |
|---|---|---|
| 加载 | 骨架行、保留筛选栏 | 详情骨架、标题占位 |
| 空 | 解释这里会出现什么 + 第一步行动 | "请选择一项查看详情" |
| 错误 | 保留可重试入口,不清空筛选 | 说明详情加载失败,可重试或返回列表 |
| 选中 | 当前行高亮,滚动后仍能识别 | 详情标题与选中对象一致 |
| 更新 | 列表行局部刷新,不整页闪烁 | 保存后显示成功反馈,必要时同步列表 |
| 删除 | 行移除 / 进入撤销状态 | 详情关闭,选中相邻对象或回空详情 |

## 反模式(AI 产物最常犯)

1. **字段平铺**:列表直接投影数据库表,没分层。
2. **无选中态**:点了行没高亮,用户不知道现在看的是谁。
3. **返回丢位置**:从详情返回后列表回到顶部,用户又得从头找。
4. **详情字段堆叠**:从上到下排字段,没分五区。
5. **状态残缺**:只有默认态,没空/加载/错误/无权限。
6. **打开方式单一**:所有情况都用整页跳转,连续处理时上下文全丢。
7. **列表只能看不能改**:明明能批量处理,却要点进详情才能操作。

## 列表-详情提示词(原文 16.7)

```
你是一位资深 B 端产品设计师。请为一个复杂对象设计列表-详情模式,
不要把所有字段平铺在列表或详情页里。

产品/对象:{任务、订单、客户、审批、工单...}
用户任务:{用户为什么打开列表?要筛选、判断、处理什么?}

请输出:
1. 列表设计
   - 第一眼必须显示的字段
   - 第二眼辅助判断的字段
   - 默认隐藏或进详情才显示的字段
   - 排序、筛选、搜索、批量操作方案
   - 空状态、加载、错误、无权限状态

2. 详情设计
   - 标题区、主信息区、属性区、关系区、历史区
   - 每一区放什么内容,为什么
   - 哪些字段可快速编辑,哪些必须进完整编辑页

3. 打开方式
   - 何时用抽屉 / 整页 / 分栏
   - 移动端如何重排

4. 交互状态
   - 选中行、高亮、保存、删除、撤销、刷新、返回位置
   - 保存详情后列表如何同步

5. 好坏对照
   - 错误方案:字段平铺、无选中态、返回丢位置
   - 专业方案:信息分层、状态完整、连续处理顺畅

要求:
- 用表格输出字段分层
- 用 Mermaid 画列表到详情的流程
- 不要写空话,每个字段必须说明它服务哪个判断
```
