# patterns/05 — 设计系统治理(防止系统腐化)

> 出处:《设计的实践》第 19、24 章(行 6970–7087、7700–7891)
> 严重度:★★ — 跳过它,设计系统会从"标准"变成"素材库"再变成"垃圾场"

## 一句话

> **组件库解决零件复用,设计系统解决决策复用。真正困难的不是建立系统,而是维护系统——半年后、一年后它还活着。**

## 组件库 ≠ 设计系统

很多团队说"我们有设计系统",其实只是有一堆 Figma 组件:按钮、输入框、卡片、弹窗、导航栏,摆在文件里看着整齐。但到真实产品里还是乱:

- 这个页面按钮 40px 高,那个页面 36px
- 这里用主色表示保存,那里用主色表示筛选
- 这里禁用态是灰色,那里禁用态只是透明度降低
- 这里错误提示在输入框下方,那里跑到页面顶部

**说明什么?** 它有"组件",没有"系统"。

```
组件库 = 零件复用(按钮、输入框可以复用)
设计系统 = 决策复用(新页面要不要抽屉、主按钮放哪、错误怎么提示、
                    空状态写什么、表格列太多怎么办、移动端怎么收敛)
```

新页面不用每次重新争论,系统里已经有原则、令牌、模式、组件、状态、文案和验收标准。

## 设计系统死在三个地方(原文 24.1)

| 死因 | 表现 | 后果 |
|---|---|---|
| **没人负责更新** | 系统第一版漂亮,半年后没人维护 | 系统过时,新需求绕过系统 |
| **新需求绕过系统** | "这次紧急,先临时实现" | 临时方案越积越多,系统被架空 |
| **旧组件没人废弃** | 系统越来越臃肿,新组件老组件并存 | 团队不知道用哪个,各自选自己喜欢的 |

最后:嘴上说"我们有设计系统",实际每个新页面还是从旧页面复制粘贴。系统从**标准**变成**素材库**,又从**素材库**变成**垃圾场**。

## 治理的七条纪律

### 1. 有 Owner

设计系统必须有人负责。不是兼职、不是"大家共同维护",是有明确 Owner。
- 谁批新组件进系统
- 谁决定老组件废弃
- 谁定期 review 系统健康度

### 2. 进系统有门槛

新组件进系统,要回答:
- 解决什么重复问题(出现 3 次以上)
- 现有组件能不能扩展解决(优先扩展,而不是新增)
- 状态矩阵是否完整(默认/hover/loading/错误/空/禁用)
- 是否有文档、例子、反例

### 3. 出系统也要有流程

老组件废弃,要:
- 标记为 deprecated(不是直接删)
- 给迁移路径(用哪个新组件替代)
- 给迁移截止时间
- 自动检测代码里的使用,提醒替换

### 4. 令牌(token)是契约

颜色、字号、间距、圆角、阴影,**只能用 token**,不能写魔法值。

```
坏: color: #5E6AD2;
好: color: var(--brand);
```

设计系统所有 token 必须有命名规则、文档、例子。

### 5. 模式(pattern)比组件重要

组件解决"按钮长什么样"。模式解决"什么时候用抽屉,什么时候用模态"。
模式 = 决策复用。这是设计系统真正的价值,参见 [patterns/ 目录](./)。

### 6. 定期审计

每月/每季度审计:
- 哪些 token 没人用(候选废弃)
- 哪些组件被绕过(可能不好用)
- 哪些页面没遵守系统(需要迁移)
- 哪些新模式反复出现(候选进系统)

### 7. AI 验收护栏(2026 年特有)

AI 生成代码最容易绕过设计系统(它不知道你的 token、不知道你的模式)。必须有:
- AI 生成前:明确告诉它只能用 token、只能用系统组件、必须遵守模式
- AI 生成后:自动化检测魔法值、检测非系统组件、检测违反模式

## 治理的反模式

### 反模式 1:大而全的第一版

```
坏的: 第一版做了 80 个组件,结果半年后 60 个没人用。
病根: 没等"重复 3 次"再进系统。
```

### 反模式 2:只建不治

```
坏的: 建了系统就不管,新组件老组件并存,每个页面都不一样。
病根: 没 Owner、没审计、没废弃流程。
```

### 反模式 3:令牌不强制

```
坏的: 文档里说"用 token",代码里到处是 #5E6AD2。
病根: 没自动化检测。
```

### 反模式 4:模式没文档

```
坏的: 组件库 50 个,但"什么时候用抽屉"没文档,大家凭感觉。
病根: 重组件轻模式,丢了决策复用。
```

### 反模式 5:AI 生成无护栏

```
坏的: AI 生成的页面用了非系统颜色、非系统组件,没人检测。
病根: 没给 AI 设护栏,也没自动化检测。
```

```

系统 token 清单:{...}
最近 10 个新页面的代码:{...}

请输出:
1. 健康度评分(0–100)
2. 死组件(没人用的):
3. 死 token(没引用的):
4. 违反系统的页面(用了魔法值 / 非系统组件):

6. 废弃清单(应标 deprecated 的):
7. 治理行动建议(本月应做什么):
```

## 给本 skill 的纪律(自我治理)

本 skill 本身就是一个"设计系统"。为防止 skill 自己腐化,每月自检:

```
□ design-judgment/ 5 张卡还在用吗?(没绕过)
□ patterns/ 5 个模式还在用吗?(没绕过)
□ visual-language/ 5 个 style 还在用吗?(没混用)
□ components/ 字典还在遵守吗?(没魔法值)
□ references/qa-* 还在跑吗?(没省略)
□ Failure Modes 库还在更新吗?(发现新模式就加)
□ examples/golden-task-manager.md 还能复现吗?(标准没降)
```

任一项答"否" → skill 已经开始腐化,需要回炉。
