# patterns/04 — 反馈决策树(Toast / Banner / Inline Error / 空状态 / 加载 / 成功感)

> 出处:《设计的实践》第 27 章(行 8236–8438)
> 严重度:★★ — 跳过它,产物会"什么都用 Toast",反馈位置错乱

## 一句话

> **反馈不是"弹个提示"这么简单。反馈要解决三件事:告诉用户发生了什么、现在处于什么状态、下一步该怎么办。只说"操作失败"不叫反馈,叫甩锅。**

## 反馈要回答的三个问题

```
1. 发生了什么?    (What)
2. 现在处于什么状态? (Status)
3. 下一步该怎么办?  (Next)
```

**只说"操作失败"= 没回答 What / 没回答 Status / 没回答 Next = 甩锅。**

正确写法:
> "网络连接中断,当前内容已保存在本地,恢复后会自动同步。"

这一句同时回答了:发生了什么(网络断)、当前状态(已存本地)、下一步(恢复后自动同步)。

## 五种反馈容器决策树

```
要反馈一件事
   │
   ▼
这件事需要用户立刻操作吗?
   │
   ├── 不需要,只是告知 ─────────────────────> Toast
   │                                          (3–5 秒消失,右下或顶部)
   │                                          重要操作带"撤销"
   │
   ├── 需要,但不阻塞当前操作 ───────────────> Banner
   │                                          (顶部常驻,可关闭)
   │                                          用于系统级提示、警告
   │
   ├── 需要,且就发生在某个字段/区域 ─────────> Inline Error / Inline Hint
   │                                          (紧贴出错位置)
   │                                          用于表单校验
   │
   ├── 没有数据,要解释为什么 + 给行动 ───────> 空状态
   │                                          (页面中心,大留白)
   │                                          用于首次使用 / 无结果
   │
   └── 等待中,要让用户安心 ─────────────────> 加载状态
                                              (骨架屏 / 进度条 / 旋转)
```

## 五种反馈容器的规格

### Toast

- **位置**:右下角(桌面)、顶部(移动)
- **时长**:3–5 秒,长文案 6–8 秒
- **必带**:操作类 Toast 必须有"撤销"按钮(5 秒内可点)
- **不要放**:重要错误、需要决策的内容、长文案

### Banner

- **位置**:页面顶部、内容区上方
- **时长**:常驻,直到用户关闭或问题解决
- **必带**:关闭按钮(可关闭时)、行动按钮
- **不要放**:成功反馈(用 Toast)、字段错误(用 Inline)

### Inline Error / Inline Hint

- **位置**:紧贴出错的字段、卡片、区域
- **时长**:直到问题解决
- **必带**:具体原因 + 解决建议
- **不要放**:全局错误(用 Banner)、操作成功(用 Toast)

### 空状态

- **位置**:页面中心
- **必带**:
  1. 解释为什么空(没数据?没权限?没结果?)
  2. 第一步行动(创建?邀请?筛选?)
  3. 视觉引导(插画 / 图标 / 按钮)
- **不要放**:简单"暂无数据"四个字(这是 AI 最常犯的)

### 加载状态

- **骨架屏**:用于已知结构的页面/卡片(优先用)
- **进度条**:用于已知耗时的操作(下载、上传、处理)
- **旋转圈**:用于未知耗时的小操作(慎用,容易让人焦虑)
- **必带**:上下文保留(加载时不要清空已显示的内容)

## 反馈的语气纪律

反馈不是技术问题,是**沟通问题**。语气错了,再准确的技术信息也救不回信任。

| 场景 | 错误语气 | 正确语气 |
|---|---|---|
| 网络断 | "网络错误" | "网络连接中断,内容已保存,恢复后自动同步" |
| 没权限 | "禁止访问" | "你需要 XX 权限才能查看,可向管理员申请" |
| 必填未填 | "请填写必填项" | "这一项不能为空(原因:用于生成合同)" |
| 删除成功 | "删除成功" | "已删除。撤销(5 秒)" |
| 保存成功 | "保存成功" | 不弹 Toast,只在按钮上显示 ✓(成功感不靠弹) |
| 操作失败 | "操作失败" | "保存失败:网络超时。已自动存草稿,可重试。" |

## 反馈的反模式(AI 最常犯)

### 反模式 1:什么都用 Toast

```
坏的: 表单错误、权限拒绝、删除成功、加载中都用 Toast。
病根: 没区分反馈的位置和紧迫性。
```

### 反模式 2:甩锅式错误

```
坏的: "操作失败"、"出错了"、"请稍后重试"。
病根: 没回答 What / Status / Next。
```

### 反模式 3:空状态只有"暂无数据"

```
坏的: 列表为空时只显示"暂无数据"四个字。
病根: 没解释为什么空 + 没给第一步行动。
```

### 反模式 4:加载时清空

```
坏的: 加载时清空已显示的内容,显示一个旋转圈。
病根: 上下文丢失,用户焦虑。
```

### 反模式 5:成功反馈太重

```
坏的: 每次保存都弹一个 Modal "保存成功!"。
病根: 成功感不靠弹,靠按钮 ✓ 和局部高亮。
```

### 反模式 6:错误没有撤销

```
坏的: 删除后只说"已删除",不能撤销。
病根: 严肃操作必须有 5 秒撤销窗口。

原文金句:撤销是给用户后悔的余地,不是技术奢侈。
```

## 反馈决策提示词

```
你是一位资深交互设计师。请为下面场景设计反馈,
不要默认"什么都用 Toast",也不要写甩锅文案。

场景:{发生了什么}
用户当时在做什么:{上下文}
紧迫性:{立刻要看 / 不紧急 / 永久保留}
位置:{全局 / 字段级 / 页面中心}

请输出:
1. 反馈容器选择(Toast/Banner/Inline/空状态/加载)
2. 反馈文案(三要素:What + Status + Next)
3. 反馈时长(几秒消失)
4. 是否需要撤销(5 秒窗口)
5. 反模式自查(是否甩锅 / 是否太重 / 是否位置错)
```
